Workflow prototype

出錯，回到對應節點

Graph 決定走哪一步，每個節點的小 loop 負責局部修正。

觸發：主題與讀者規格已確認。目標：五篇以上來源的 Wiki 與 15 頁 HTML。完成條件：來源可追溯、逐頁對應、檢查通過、保留限制。停止條件：缺來源、同一節點三輪未通過，或修正沒有進展，就記錄缺口並停止。

節點的輸入、輸出與退回規則

節點輸入 / 輸出檢查與失敗路線
A 需求對話 / discussion.md、AGENTS.md使用者確認主題與規格後開始
B、G1 取得資料固定版本 PDF / manifest、來源文字逐篇檢查可讀性與定位，失敗只重取該篇
C Wiki單篇原文 / sources、concepts、index、log檢查來源與互連；矛盾保留條件，錯卡重整該卡
G2 查詢Wiki 索引與題組 / 檢索結果缺主題就先補索引，再進簡報，最多三輪
D、G3 逐頁稿大綱與概念卡 / slides.json、slide-map.md來源可支持才通過，錯誤只修對應頁
E、G4 渲染通過稿 / index.html、瀏覽檢查檢查頁面與互動；內容變更回 D，版面修正留在 E
F 交付通過成果 / 完整作業與紀錄紀錄仍有的限制，不把腳本通過視為滿分保證

為什麼這樣設計

檢索不到資料時，先處理索引比先寫簡報再補洞省事。把來源核對與版面檢查分開，可以保留已通過的內容，只修改出錯的局部。每次修正後仍要重跑受影響的檢查，以免新增斷鏈或來源錯配。

本作業是由 Codex 執行、檔案保存狀態的 workflow prototype。沒有宣稱部署無人值守的自主代理。大綱由同一製作流程依已確認規格審查，沒有偽稱使用者逐頁簽核。
