本 HTML 可離線開啟，不需套件、帳號或網路。只有「閱讀原文」會連線。瀏覽器列印會輸出全部簡報及附錄。

我的主題筆記

先找到證據，再請 AI 回答

我把五篇資料拆成七個互相連得起來的概念。第一次看 RAG，可以先照目錄讀；想查特定詞，也可以直接搜尋。

每個概念都保留來源章節、相關概念和簡報頁面的反向連結。我另外把論文限制寫下來，避免把研究結果講得太滿。

我的製作流程

哪裡出錯，就回去修哪裡

我沒有每次都把整份作業重做，而是把資料、檢索、內容和版面分開檢查。

開始前：先確認主題和讀者。完成標準：至少五篇來源、Wiki 與簡報能互相對照、檢查通過，而且研究限制不能被省略。停止條件：同一節點連續三輪仍沒改善，就留下紀錄，不讓流程一直空轉。

節點的輸入、輸出與退回規則

節點輸入 / 輸出檢查與失敗路線
A 需求對話 / discussion.md、AGENTS.md使用者確認主題與規格後開始
B、G1 取得資料固定版本 PDF / manifest、來源文字逐篇檢查可讀性與定位，失敗只重取該篇
C Wiki單篇原文 / sources、concepts、index、log檢查來源與互連；矛盾保留條件，錯卡重整該卡
G2 查詢Wiki 索引與題組 / 檢索結果缺主題就先補索引，再進簡報，最多三輪
D、G3 逐頁稿大綱與概念卡 / slides.json、slide-map.md來源可支持才通過，錯誤只修對應頁
E、G4 渲染通過稿 / index.html、瀏覽檢查檢查頁面與互動；內容變更回 D，版面修正留在 E
F 交付通過成果 / 完整作業與紀錄紀錄仍有的限制，不把腳本通過視為滿分保證

為什麼這樣安排？

如果資料根本找不到，先修索引會比簡報寫完才補洞省事很多。來源內容和畫面也要分開檢查：文字有問題就回到對應頁稿，排版有問題才回到 HTML。這樣能保留已經確認過的部分，也比較容易看出這次到底修了什麼。

這是一個有實際檔案與檢查紀錄的工作流程原型，並不是部署在伺服器上、會自己運作的代理程式。
